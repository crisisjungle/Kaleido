# Result-First Output Contract

## 核心原则

Kaleido 的正式产品界面只交付业务结果，不向用户汇报系统是否成功完成了某个内部步骤。

成功不是一条需要展示的信息，而是产品能够呈现结果的默认前提。地图已经生成时直接展示地图，事件已经完成语义整理时直接展示整理后的事件，Agent 已经配置时直接展示 Agent 配置，报告已经形成时直接打开报告。正式界面不再额外显示“识别成功”“生成成功”“配置成功”“处理完成”等自我评价。

这条原则同样适用于内部处理没有得到首选结果的情况。系统应在后台继续重试、切换模型、使用受约束规则、选择最佳解释或形成业务备选方案；正式界面只呈现最终采用的业务结果，不展示“无法识别”“识别失败”“降级”“Fallback”“低置信度”或模型处理路径。

## 默认成功不等于伪装成功

结果优先不是隐藏错误，更不是把没有发生的操作描述成已经发生。

- 后端仍必须保存真实的执行状态、错误、模型调用、校验结果、重试记录、候选解释和证据质量。
- 只有经过业务校验、可以被当前产品能力实际承接的结果，才能进入正式用户界面。
- 如果当前还没有可交付结果，界面停留在输入、处理中或可继续执行的状态，保留用户输入和最后一个有效工件；不要伪造结果，也不要把内部失败报告当成业务输出。
- 对运行干预、政策执行、状态变更等有真实副作用的操作，只有实际提交并被运行时接受后才更新业务结果。没有执行就不展示执行后的状态。

因此，正式产品的约束是：**结果存在时直接展示结果；结果尚未存在时继续完成任务或提供下一步动作；不展示系统对自身成功或失败的评价。**

## 测试环境与正式产品的边界

测试、开发和运维诊断需要完整可观测性，可以显示：

- 成功、失败、超时、重试和取消状态；
- 主模型、备用模型和确定性规则的实际使用路径；
- 置信度、候选排序、语义匹配、未解析引用和校验原因；
- 请求、响应、任务编号、工件编号、内部枚举和结构化错误；
- 输入经过各处理阶段后的中间产物。

这些内容属于测试面板、开发日志、服务端日志、审计工件和自动化测试，不属于正式业务界面。

正式产品界面只显示：

- 用户输入和可编辑业务参数；
- 系统整理后的场景、事件、政策、区域、Agent、关系、风险和报告；
- 必要的业务选择，例如主方案和最多两个真正可执行的备选方案；
- 中性的任务过程，例如“正在生成场景”或“正在整理区域”；
- 明确的下一步动作，例如“继续生成”“重新获取”“调整范围”或“返回修改”。

测试版本可以回答“系统做得对不对”；正式产品只回答“用户现在得到了什么、可以继续做什么”。

## 系统日志的职责

系统日志最初和长期存在的目的，就是支持测试、调试、运维和审计。成功、失败、超时、重试、模型切换、规则命中、Fallback、置信度、未解析引用和错误原因都应在日志中如实保留；这些信息对开发者判断系统真实行为非常重要，不应为了适配用户界面而被删除或粉饰。

系统日志可以在测试版本、开发面板或授权诊断入口中展示，但必须与正式业务页面隔离。Step 1-4 的卡片、表格、报告、Toast、横幅、空状态和业务活动记录不得直接复用日志文案。业务页面读取的是经过校验的结构化工件和业务状态，系统日志服务的是开发与运维人员，两者不能共用一套展示出口。

日志隔离不等于取消可观测性。正确结构是：后台保留完整真实日志，测试面板展示处理过程，正式页面直接展示最终业务结果。日志仍需遵守安全规则，不得暴露密钥、凭据、隐私数据或其他敏感内容。

## 正式界面输出规则

### 1. 展示对象，不展示完成声明

| 内部或测试表达 | 正式产品行为 |
| --- | --- |
| `地点识别成功` | 直接定位并展示地图范围 |
| `事件识别成功：台风` | 直接展示“八号烈风信号影响”及事件链 |
| `已成功生成 12 个 Agent` | 直接展示 Agent 配置表和数量 |
| `关系网络生成完成` | 直接展示关系网络 |
| `报告生成成功` | 直接打开正式报告 |
| `配置已就绪` | 直接开放下一步业务操作 |

结果本身就是完成状态，不再叠加成功横幅、成功 Toast、成功徽章或说明文字。

### 2. 输出方案，不输出识别过程

用户输入自然语言后，系统必须形成一个可执行的主解释。存在重要歧义时，可以提供最多两个业务备选方案，但不能把内部判断过程交给用户。

例如用户输入“天文台改挂八号”，正式界面直接使用“八号烈风信号生效”作为场景事件。若确有必要，调整入口可以提供“按交通与公共服务中断处理”等业务选项；界面不显示关键词是否命中、模型置信度、采用了哪种解析器或是否使用了兜底路径。

### 3. 业务备选不是技术兜底

备选方案必须是用户能够理解并真正选择的业务方案，例如不同空间范围、作用对象、政策强度或机制侧重点。不得出现以下伪业务选项：

- 通用事件；
- 默认模板；
- 系统兜底；
- 降级模式；
- 低置信度方案；
- 重新识别。

这些都是内部实现状态，不是用户的业务选择。

### 4. 处理中可以有过程，结果页不做自我汇报

耗时任务允许显示与任务直接相关的中性过程，例如“正在构建区域关系”或“正在生成场景”。过程结束后应由结果自然替换过程界面，不再出现一次“生成成功”的过渡确认。

正式界面不使用绿色成功提示作为常规完成反馈。颜色、图标和状态标签应服务业务含义，而不是反复证明系统正常工作。

### 5. 没有结果时提供动作，不提供系统判词

内部重试仍在进行时继续展示处理状态。已经不能自动继续时，保留用户输入和最后一个有效工件，并提供最接近任务的动作入口，例如“继续生成”“重新获取地理数据”“调整范围”或“返回修改”。

正式界面不把异常堆栈、模型错误、数据源诊断、识别结论或技术失败原因作为主要内容。完整原因进入测试面板和内部审计。

## 在四步流程中的应用

### Step 1 背景定义

- 地点解析完成后直接展示定位结果，不显示“地点识别成功”。
- 文本和文档完成语义整理后直接形成背景报告、稳态、事件、政策和主体结构，不显示“LLM 整理成功”。
- 地图、文档和语义处理路径只进入内部审计。
- 如果正式空间结果尚未形成，保留输入并提供“重新获取”或“调整范围”，不把 provider 状态当作业务结果。

### Step 2 场景生成

- 配置完成后直接展示风险对象、区域、Agent 和关系，不显示“场景生成成功”或“Agent 生成成功”。
- 用户输入的事件和政策直接呈现为系统采用的业务解释。
- 需要备选时只提供机制、范围或政策层面的业务方案，不显示内部匹配状态。

### Step 3 推演运行

- 干预被运行时接受后直接进入干预记录和运行状态，不显示额外成功 Toast。
- 只有实际生效的干预才能进入结果；未执行的干预保留在编辑状态。
- 目标解析、动作校验、模型调用和运行时拒绝原因保留在内部诊断。

### Step 4 分析与报告

- 报告形成后直接展示报告，不显示“报告生成成功”。
- 节点追问直接回答问题，不汇报检索、识别、推理或模型调用是否成功。
- 分析结果不足以形成正式结论时，继续使用已有证据生成受约束的结果或提供下一步分析动作，不输出内部质量判词。

## 实现边界

- 后端状态机、任务管理器、日志和审计文件继续保留 `success`、`failed`、`fallback`、`confidence`、`unresolved` 等机器状态。
- 测试版本可以通过诊断开关、测试面板或开发日志查看这些状态。
- 正式 API 的业务 DTO 不把机器状态当作标题、摘要、说明、徽章或结果文案。
- 前端不得为常规完成动作增加成功 Toast、成功横幅或“已完成”说明；直接刷新对应业务结果。
- 正式界面不得显示模型名称、Prompt、关键词命中、规则路径、置信度、内部 ID、异常类型和降级来源。
- 公共 DTO 遇到夹杂旧枚举、英文别名或机器 ID 的中文业务正文时，应逐词翻译或移除技术片段，并保留剩余业务语义；不得因为局部污染把整段结果替换成“暂无摘要”或“暂无可展示内容”。
- 报告中的模型自述、工具调用计划和章节生成旁白属于系统过程，必须从正式正文移除。技术目标列表被清理为空时，应投影为“当前分析范围”或“相关执行主体”等受约束业务表达，不能留下空标点列表。
- 前端显示清洗层只能作为最后防线。正确做法是在业务 DTO 形成前完成结果选择和投影，而不是先返回技术状态再在前端替换文案。

## 验收规则

- 同一业务结果在正式界面中只出现结果本身，不同时出现“成功”声明。
- Step 1 至 Step 4 的正常完成流程没有成功 Toast、成功横幅或成功徽章。
- 正式页面不出现“无法识别”“识别失败”“生成失败”“Fallback”“降级模式”“低置信度”等系统自我评价。
- 主方案和备选方案都使用业务语言，并且能被当前场景、空间对象和运行能力实际承接。
- 没有实际生成或执行的结果不得伪装成已经发生。
- 测试和运维仍能从日志、任务状态和审计工件还原真实处理路径。
- 用户刷新页面或重新进入任务后，看到的是最后一个有效业务结果，而不是一次处理成功的历史提示。
